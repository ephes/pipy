## What Changed

This slice brings pipy up to Pi `0.80.6` on the GPT-5.6 Sol Codex model and the
`max` thinking level.

- **New built-in Codex model.** `openai-codex/gpt-5.6-sol` (displayed as
  `GPT-5.6 Sol (Codex/ChatGPT)`) is now a selectable catalog row with a 372K
  context window and image input. It builds through the existing legacy Codex
  provider factory, so its retry policy, OAuth, and transport behavior are
  unchanged; only the request's `reasoning.effort` is new. GPT-5.5 remains the
  Codex default and no bare `gpt-5.6` alias is added.
- **A seventh thinking level, `max`.** The canonical vocabulary is now
  `off|minimal|low|medium|high|xhigh|max` everywhere a level is accepted or
  stored: the CLI `--thinking`/`:level` suffix, `settings.json`'s
  `defaultThinkingLevel`, extension controls, the RPC surface, and `models.json`.
  Unknown levels still warn and fall back.
- **Model-aware Shift+Tab cycling.** The reasoning-level cycle is no longer a
  fixed five-level list. Every reasoning model cycles the ordinary tier
  (`off|minimal|low|medium|high`) and appends `xhigh`/`max` only when the active
  model actually maps them — matching Pi's `getSupportedThinkingLevels`. Sol
  cycles all seven; opus and gpt-5.5 now also cycle `xhigh`; models that map
  neither stay on the five ordinary levels.
- **Codex clamp-then-map into `reasoning.effort`.** Previously an unsupported
  stored level was silently dropped. Now, at the point the Codex provider is
  built, the stored level is clamped to the nearest level the current model
  supports and then mapped, reaching the request as `reasoning.effort` — a
  faithful port of Pi's per-request `clampThinkingLevel`. A stored `max` sends
  `effort: "max"` on Sol, clamps to `xhigh` on gpt-5.5, and to `high` on
  gpt-5.4/gpt-5.1-codex; `off`/unset still omits `effort` and keeps only the
  Pi-forced `summary: "auto"`. Because a level is resolved on each provider
  build, Shift+Tab, extension, or model-switch changes take effect on the next
  turn.
- **372K status budget.** Sol renders its context usage against a `372k`
  denominator instead of the generic Codex `272k`.

## Visualization

The one genuinely new runtime behavior is the clamp-then-map that resolves a
stored level into a Codex request effort:

```mermaid

    A[stored thinking level] --> B{level is None or off?}
    B -- yes --> Z[omit reasoning.effort<br/>summary: auto only]
    B -- no --> C[clamp to nearest level<br/>the model supports]
    C --> D[map clamped level via row's<br/>thinking_level_map]
    D --> E[reasoning.effort = mapped value]

    E -. Sol, stored max .-> E1["effort: max"]
    E -. gpt-5.5, stored max .-> E2["effort: xhigh (clamped)"]
    E -. gpt-5.4, stored max .-> E3["effort: high (clamped)"]
```

## Boundaries

Held deliberately out of scope, mostly as named follow-ons:

- **Generalized cross-provider clamping.** The clamp lives only at the Codex
  effort-resolution boundary. Every other provider keeps its existing
  *omit*-on-unsupported behavior; unifying clamp-not-omit across all providers
  and effort-label surfaces is the one explicitly named follow-on.
- **Other GPT-5.6 distributions and rows.** No `openai/gpt-5.6-sol`, Azure,
  OpenRouter, Vercel, Terra, or Luna rows; no bare `gpt-5.6` alias.
- **Pricing.** Sol keeps pipy's zero-cost subscription convention; long-context
  API pricing tiers and billing calculations are untouched.
- **No default change.** GPT-5.5 stays the Codex default; no provider default is
  altered.
- **RPC stays state-only for `max`.** `max` is accepted as a stored/reported RPC
  value exactly like `off…xhigh`; it does not trigger live provider propagation,
  which remains deferred for every level.
- Default-thinking-precedence changes, theme-schema changes, and unrelated July
  Pi extension hooks are also out of this slice.

## Comprehension Check

<details>
<summary>Why does the Codex path now clamp an unsupported level instead of dropping it, and why only Codex?</summary>

Adding `max` newly lets a user cycle Sol to `max` and then switch to a Codex
model that lacks it (e.g. gpt-5.5), leaving a stored-but-unsupported level.
Silently omitting it would *worsen* reachability, so the slice ports Pi's
per-request `clampThinkingLevel` to the nearest supported level. It is scoped to
the Codex request path because that is exactly where Pi clamps; generalizing the
clamp across providers is a named follow-on, not this slice.
</details>

<details>
<summary>Sol's row spells out ordinary levels like <code>low</code> and <code>medium</code> even though Pi's map omits them. Why?</summary>

Pi's Sol map is `{"xhigh":"xhigh","max":"max","minimal":"low"}` and treats an
unmapped, non-`null` ordinary level as identity-supported. Pipy instead derives
support from the map's keys, so the row must list the ordinary levels
explicitly to offer them. Note `minimal → "low"` is a non-identity mapping taken
straight from Pi's Sol row.
</details>

<details>
<summary>A stored <code>max</code> is active. What effort reaches the request on Sol versus on gpt-5.5?</summary>

Sol maps `max`, so it sends `reasoning.effort: "max"`. gpt-5.5 maps `xhigh` but
not `max`, so the clamp walks down to `xhigh` and the request carries
`effort: "xhigh"`. (On gpt-5.4/gpt-5.1-codex, which map neither, it clamps to
`high`.)
</details>
