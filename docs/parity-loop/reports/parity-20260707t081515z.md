## What Changed

This slice turns `ctx.ui.set_editor_component(...)` from an inert live-session
store into an active custom editor integration. In a live product TUI, pipy now
calls the extension's editor factory, installs the returned component in the
main input area, renders the component's rows, and routes decoded key presses to
its `handle_input`/`handleInput` method instead of double-processing them through
the built-in editor. Component submit/change callbacks keep pipy's core input
buffer mirrored, submitted text becomes the next prompt, and clearing or factory
failure falls back to the built-in editor without losing the draft.

The live extension UI driver now delegates editor-component state to the
terminal UI, so `get_editor_component()` reflects whether a live component is
installed. Existing extension autocomplete providers are resolved and forwarded
to custom editor components that expose `set_autocomplete_provider` /
`setAutocompleteProvider`, including through the public `read_line` path.
Headless/RPC-like contexts keep their safe no-op behavior.

## Boundaries

This is live custom-editor rendering/input integration, not full Pi component
library parity. Pipy still does not expose Pi's full editor action-handler map,
so built-in exit/model/thinking hotkeys are not automatically copied into custom
editors; components must handle submit/cancel semantics themselves. Broader
custom component APIs, overlay focus behavior, remote package ecosystems, and
other extension-platform follow-ons remain outside this slice.

component failures fail soft to the built-in editor instead of crashing the
session or persisting extension UI internals.
