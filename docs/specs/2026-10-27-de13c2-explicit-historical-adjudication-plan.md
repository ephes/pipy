# DE13c2 explicit historical tool adjudication

## Scope and operation

Add `DurableProductSession.adjudicate_interrupted(task_id, *, nonce)` and `pipy durable adjudicate-interrupted --task … --nonce …` through the native product composition. This is explicit authorization to end an uncertain old model-tool attempt without invoking it. It is not automatic resume, a tool-specific success verifier, or authorization for a new attempt. `authorize_retry` and its ANY-receipt fence remain unchanged.

The operation returns a bounded immutable decision acknowledgement `{task_id, decision}`, where decision is `interrupted` for a newly committed uncertain receipt or `receipt` for preservation of an existing supported first winner. It does not claim task completion, provider continuation or absence of an effect. Ordinary explicit `resume()` performs subsequent settlement and next-provider work; a retry-successor root still requires its existing `DurableRunSelection`. CLI emits only the decision acknowledgement, without implicit resume. Fresh admission requires a matching provider profile and checks actual selection, header/root lineage, workspace and catalog. CLI/profile construction can read and retain credential material from the environment, AuthStore and models.json; adjudication neither uses or refreshes those credentials nor invokes a provider. Actual material/transport preparation and reconstruction checks remain at the subsequent generation PREPARE/request, not fictional decision-time checks. No new public scheduler mode is introduced.

A validated same-nonce winner may be replayed without a profile, including CLI omission of both `--provider` and `--model`; this path does not construct a provider profile. Existing ownership, actual header/workspace/root lineage, nonce and winner bindings still apply. If a profile is supplied, selection mismatch with the header is `incompatible` for both fresh admission and same-nonce replay. A missing winner with no profile yields `profile_required` before any mutation; auth-free replay cannot authorize a fresh decision or resume. Partial profile arguments remain invalid CLI input.

The new SDK operation exposes fixed refusals as `DurableProductError`. Translate its private policy errors at this operation boundary and explicitly add `stale`, `conflict`, `not_supported`, `receipt_held_needs_repair` and `retained_control` to that error's allowed codes; preserve existing codes including `busy`, `closed`, `incompatible`, `profile_required` and `unavailable`. Do not change retry's exception translation. For this command, acknowledgement exits 0; fixed operation refusal exits 1 and prints `Durable command unavailable: <code>` to stderr with no acknowledgement payload. Syntax/argument errors emit the fixed `invalid_request` code and exit 2; signal/ownership cleanup retain existing CLI handling. Unknown private failures remain `unavailable`, never payload-bearing.

## Finite evidence and refusal

Only a supported pending `pi.tool` blocked record, directly model-owned in a valid waiting tools round, can be freshly adjudicated. Prove CID, task/input, parent, assistant, call correlation/name, selected slot, exact saved request/offer, prefix results, saved key and workspace. Retain current leaf/ownership and later-slot/terminate restrictions; for new interrupted synthesis refuse any owned descendant task or conversation rather than implying general nested cleanup. Abort-marked, background, abandoned, unknown-version or malformed authority refuses without mutation.

Eligibility is evidence-based, not a claim about historical cause. Supported closed blocked reasons may be uncertain, incompatible or invalid_result. An explicit operator can conservatively end an intact uncertain attempt even when ordinary failure and reporting-infrastructure loss cannot be distinguished. The operation never labels the latter safe, ordinary, or successfully executed. Reason, version and missing progress are not provenance evidence.

Receipt presence has four distinct cases, checked from actual committed document metadata without seeding:

1. **Document absent:** new interruption requires the blocked record's intact validated non-null prepared intent.
2. **Known document, exact default-empty `{}`:** the same intact-intent requirement applies. Explicit C2 authority may replace this known empty default with an uncertain receipt; this is not a relaxation of retry's document-existence fence. Unknown document version, malformed address/scope or inconsistent record metadata never counts as empty.
3. **Nonempty supported valid receipt:** it is the first winner. Its actual non-null intent must bind saved header/offer, call/key/workspace and the model-owned graph. If the blocked frame has an intent it must match; if the frame is intent-less, use the actual receipt's saved intent, never reconstruct one from the call. Preserve the receipt's full fact, completion time, counters and controls exactly. A valid existing receipt takes precedence over current restart metadata and retained-progress contents. Existing legal control behavior remains unchanged; a retained terminate control may hold continuation rather than inventing a next answer.
4. **Opaque, malformed, newer or mismatched receipt:** fixed `receipt_held_needs_repair`, no overwrite, deletion, fallback synthesis or retry. A valid receipt with no intent is outside this migration because it cannot establish the saved invocation authority needed here; retain it for a later explicit authority-repair slice.

Receipt-absent/default-empty intent-less blocked records refuse `not_supported`. They include genuine pre-intent incompatibility and cannot acquire invented prepared arguments or keys. For a new interruption, require absent/default-empty or strictly matching supported progress. Preserve committed output, details presence and diagnostics. Invalid progress refuses `incompatible`; absence gives empty output, absent details and unknown attempts. Counters use C1's exact required nullable shape; invalid present current restart source refuses before writes, and missing remains null. No cumulative attempt count or DE14 policy is inferred.

## Atomic decision, ownership and idempotency

Use the existing product `_owned` control, PathOwner and Session transaction line. The operation does not construct/open a scheduler just to decide. With no scheduler, perform the owned Session-line operation directly. With a cached scheduler, inspect actual lifecycle under its existing guard, including `_opened`, `_owner._failure`, sealed line and host completion. A failed, sealed, ended or not-opened cached owner refuses `closed`. The serialized `_owned` control prevents a later operation from observing a legitimate opening in progress; do not invent an externally visible retryable opening state. `_opening` is not independently a closed test, because delivered successful recovery leaves it set. Reserve `busy` for genuine active-control/reservation conflicts. A healthy opened scheduler is paused and genuinely drained; `apause` itself must not open/reconcile it. No mirrored lifecycle flag is added. Public control prevents a competing product resume from re-enabling dispatch while the decision is in flight. Existing invocation/parent reservations are rechecked on the Session line; metadata guards never contain copying, storage work, foreign callbacks or joins.

Capture an owned private target containing actual task/graph/round/header and opaque receipt identity/value. Select receipt-first dependencies on that same Session line. A valid supported winner does not depend on parsing, comparing or validating irrelevant current progress or restart metadata. Only absent/default-empty synthesis captures and validates retained-progress identity/value and current restart source; those then participate in expected-state revalidation. Pure public preflight occurs before any scheduler opening, document acquisition or Store write. On the committing Session line, first resolve a valid same-operation nonce winner, otherwise recapture and compare the expected target and revalidate all graph/catalog/evidence predicates. No check-then-mutate window may cross that line.

One atomic commit creates a private conversation-scoped adjudication audit, preserves the actual existing receipt or installs one C1 interrupted receipt2, and changes the SAME task to pending `settle` with that receipt's saved key. It creates no tool task, does not replace the parent's slot, and does not append a model entry in operator code. The existing tool settlement remains the sole entry producer: normal fact1 form stays unchanged, fact2 has one actual receipt carrier and one arena. Pure shared construction/validation may be extracted from existing C1 logic; no new wire codec or permissive reader path is introduced.

Use a separate private `pipy.operator.adjudication` family with a closed versioned record, not the existing retry AUDIT that requires `new_task_id`. Store the action/proposal, original task authority, decision and versioned bindings to the actual selected receipt and its supported settlement projection; do not store a parallel full outcome. Deterministic fingerprints may use existing canonical encoding plus standard ASCII JSON emission without changing that format. Audit contents are private. Validate the closed audit and original authority on every replay, then validate the actual current state according to its shape:

- Before terminal retirement, a supported settle checkpoint requires the actual receipt and saved settle call/key authority to match the audit's receipt binding. This includes a crash-persisted running settle after its old process has ended, not permission to bypass a live invocation; existing PathOwner and drain/guard checks remain required.
- After v2 settlement, validate the actual single `nativeToolReceipt` carrier and its full receipt binding, together with the existing entry/terminal graph predicate.
- After v1 settlement, validate actual `{nativeToolOutput, call, key}` against the audit's v1 projection binding and the existing entry/terminal graph predicate. The removed intent/full receipt is not reconstructed or required from the entry.
- After a later abort or scheduler fault, validate actual task identity, CID, kind/version and the closed terminal `aborted` or `faulted` outcome against the recorded original authority and validated audit identity. No settlement entry or retired receipt is required. Do not infer a cause from error text. This acknowledgement attests only the recorded decision, never settlement, effect absence or success.
- After settle validation reblocks the task, accept replay only for the supported pending `blocked`/version 1/`incompatible`/`intent=None` checkpoint with the exact original call. Require the actual still-present receipt's document identity, scope/address/version and full value binding to match the committed audit; validate the supported receipt and its call/key against the saved authority. An absent, replaced, changed, opaque, malformed or mismatched receipt is `incompatible` on this replay path. Do not reconstruct the cleared blocked intent, install a replacement receipt, clear the block or imply permission to resume.

Completed/failed settlement replay retains exact entry ownership, one-arena and actual outcome/control predicates. Aborted/faulted decision-only replay is the explicit exception to requiring an entry. Unknown current state shapes, mismatched task/audit bindings, and unsupported reblocked shapes refuse `incompatible`. No audit payload substitutes for a missing settlement entry; no corrupted receipt replacement can gain acknowledgement merely because an audit exists.

Nonces are scoped by conversation AND operation. Same adjudication nonce/proposal returns the same committed acknowledgement across cancellation, close/reopen and the supported settle, terminal or receipt-stable reblocked states above; corrupted or unsupported states retain the specified fixed refusal. Same adjudication nonce with a different task/proposal is `conflict`. A nonce used for retry is a separate operation namespace and does not confer adjudication authority; either operation still needs its own state/evidence predicate. A second nonce cannot apply a second decision to an already transitioned task. Audit acknowledgement denotes a committed decision, not current completion: later abort, scheduler fault or supported validation reblock may prevent continuation and must not be undone or reported as success.

If a real receipt or other authority changes after target capture, return `stale` without installing an audit or replacement; a fresh call may then preserve that receipt. If abort wins first, refuse without mutation. If adjudication wins first, later abort follows ordinary scheduler semantics. Concurrent adjudication/retry, duplicate calls and late completion serialize on the existing line; only one applicable transition wins. Caller cancellation does not cancel an admitted operator commit or release its lease/owned work early. Commit-success/ACK-loss replays the durable nonce winner; uncertain commit failure never fabricates ACK or silently retries mutation.

## Public catalog admission

Validate actual product header, selected root lineage, profile selection, workspace and catalog before fresh mutation. Provider material/transport binding remains at subsequent PREPARE/request. Do not rewrite the header or normalize normal snapshots. Same catalog retains original saved request members and serialization. Missing/changed current tools may authorize only this noninvoking decision, never old invocation.

For a changed whole catalog, validate the proposed target as receipt-backed settlement and require every other unresolved state to be an existing C1 noninvoking execute or valid settlement. Refuse pre-intent children, old persisted provider requests, other blocked states and any required safe replay, even when the safe tool itself is unchanged. Restoring the saved catalog is a positive control. The subsequent request uses the existing saved-order/saved-member intersection; new current tools cannot enlarge authority. Revalidate actual header/round at the operator commit and subsequent PREPARE_DOC transaction. A cached incompatible driver is refused, not swapped or mutated. Replaying an already committed nonce is read-only under the ownership/header/root/winner guards above; an optional supplied profile is selection-checked. Replay does not require fresh current-catalog admission and does not grant permission to resume under a new catalog.
